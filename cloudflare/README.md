# RoundUp — спільне середовище (перший робочий етап)

Це **окремий, поки що необов'язковий** сервер для спільної бази. Він не змінює роботу Windows-програми RoundUp 6.3.2, оригінального GeoZamir, імпорту ZIP, проєктів, маршрутів, фотографій або лаунчера.

**Стан:** Cloudflare Worker і D1 розгорнуті через GitHub Actions. Нативна Windows-панель підключається до API без посереднього проксі, персональний ключ лежить у Windows DPAPI. Створення об’єктів, призначення менеджерів, історія виїздів, текстові примітки, чат і періодична перевірка сповіщень реалізовані. Є **ручне публікування локальних GPS-точок** без зміни або видалення оригіналів. **Фото, ZIP, маршрути та контури поки не синхронізуються**: вони залишаються в локальній базі.

## Як працюють права

- Адміністратор (керівник) бачить усі об'єкти, створює/блокує менеджерів, призначає доступ до кожного об'єкта, може змінювати об'єкти й читати їхню історію.
- Менеджер може створити новий об'єкт зі статусом pending. До призначення він бачить свій новий об'єкт; інші менеджери — ні.
- Керівник призначає одному об'єкту одного або кількох менеджерів. Після призначення доступ мають **лише призначені** користувачі й керівник (навіть якщо інший менеджер був автором об'єкта).
- Менеджери не можуть призначати доступ через API, навіть якщо підмінять запит у клієнті.
- Нові виїзди та повідомлення — додаткові записи; зміна об'єкта має номер ревізії, щоби не перезаписати випадково зміни з іншого ПК.
- Чат і фото прив'язуються до стабільного ID об'єкта, не до назви ZIP-файлу. Фотосховище R2 буде підключене окремим етапом.

## Як увійти у Windows RoundUp

1. Відкрити збірку з GitHub Actions **RoundUp-Shared-Workspace-Windows-Preview** або встановити версію, в якій інтегрована ця гілка. Старий лаунчер не оновлюється, поки зміни не потраплять до стабільного випуску.
2. Відкрити RoundUp → **Дії** → **☁ Спільне середовище**. Вбудований GeoZamir продовжує працювати як раніше.
3. **Перший запуск керівника:** вибрати створення спільної бази, вказати ім'я й вставити значення GitHub секрету `ROUNDUP_SETUP_SECRET`. **Саме значення**, не назву ключа. Сервер дозволяє цей крок рівно один раз.
4. Далі керівник натискає **+ Менеджер**, вводить ім'я (наприклад, Олег Львів), копіює виданий персональний ключ і передає менеджеру приватно. Менеджер вставляє його в екран входу.
5. Керівник відкриває картку об'єкта → **Відповідальні** → відмічає менеджерів → **Зберегти призначення**. Права перевіряються самим сервером у кожному запиті.
6. Новий об'єкт: **+ Об'єкт**. Публікація наявних GPS-точок: **↑ Локальні точки**; після підтвердження дані потрапляють до хмари, до 100 нових точок за один запуск; повторний запуск продовжує далі й пропускає наявні. Передаються координати, назва, дата та текстові примітки; фото, ZIP і маршрути поки локальні.
7. Щоб керівник міг зайти на іншому комп'ютері: натиснути **🔑 Мій ключ** (копіюється власний ключ до буфера) і ввести його у RoundUp на іншому ПК. Берегти ключ як пароль.

Публічний endpoint перевірки: https://roundup-workspace-api.moriarty-soa.workers.dev/v1/health

**Важливо:** наявні менеджерські локальні профілі архівів і нові облікові записи Cloudflare — різні сутності. Автоматичної прив'язки історичних профілів та фотографій на цьому етапі ще немає. Одноразово призначте відповідальних керівником.

## Розгортання на власному Cloudflare

Потрібні: Cloudflare акаунт із доступом до Workers/D1, Node.js і Wrangler (можна запускати командою npx). Команди виконуються в каталозі cloudflare:

1. Створити копію конфігурації: cp wrangler.jsonc.example wrangler.jsonc (у PowerShell: Copy-Item wrangler.jsonc.example wrangler.jsonc).
2. Авторизувати Wrangler: npx wrangler login.
3. Створити D1: npx wrangler d1 create roundup-shared.
4. Замінити REPLACE_WITH_THE_ID_RETURNED_BY_WRANGLER_D1_CREATE на отриманий database_id у файлі wrangler.jsonc.
5. Створити таблиці: npx wrangler d1 execute roundup-shared --remote --file=./schema.sql.
6. Задати початковий секрет: npx wrangler secret put ROUNDUP_SETUP_SECRET. Вставити випадковий рядок довжиною **щонайменше 32 символи**. Не використовувати пароль від GitHub чи Cloudflare.
7. Опублікувати Worker: npx wrangler deploy.
8. Один раз викликати POST /v1/setup із заголовком X-RoundUp-Setup-Secret (значення із кроку 6) та тілом {"displayName":"Керівник"}. У відповіді буде **одноразово виданий** apiToken адміністратора, який потрібно зберегти в захищеному сховищі. Повторна ініціалізація заборонена на рівні D1.
9. Адміністратор створює менеджерів через POST /v1/users і передає кожному тільки його персональний ключ доступу. Ключі неможливо отримати повторним читанням бази; доступні блокування та перевипуск.

> Не записуйте секрети, токени, дані клієнтів або робочі фото у GitHub, README, знімки екрана чи вихідний код. Для Windows-клієнта зберігайте персональні токени в захищеному системному сховищі, а не в HTML/localStorage.

### API

Для всіх запитів, окрім /v1/health та /v1/setup, потрібен заголовок Authorization: Bearer ru_... .

| Метод і шлях | Призначення |
|---|---|
| GET /v1/health | Перевірка доступності API |
| POST /v1/setup | Одноразове створення керівника за секретом |
| GET /v1/me | Поточний користувач |
| GET /v1/users | Список менеджерів (тільки керівник) |
| POST /v1/users | Створити менеджера, отримати одноразовий ключ (керівник) |
| PATCH /v1/users/:id | Заблокувати / розблокувати менеджера (керівник) |
| POST /v1/users/:id/rotate-token | Перевидати ключ менеджера (керівник) |
| GET /v1/objects?after=:uuid | Авторизований список об'єктів (пагінація) |
| POST /v1/objects | Створити об'єкт; підтримує клієнтський UUID для повторної відправки |
| GET /v1/objects/:id | Картка об'єкта (перевірка прав на сервері) |
| PATCH /v1/objects/:id | Оновити картку за expectedRevision |
| GET /v1/objects/:id/assignments | Відповідальні менеджери |
| PUT /v1/objects/:id/assignments | Призначити список userIds (тільки керівник) |
| GET/POST /v1/objects/:id/visits | Історія і нові виїзди |
| GET/POST /v1/objects/:id/messages | Повідомлення в чаті об'єкта |
| GET /v1/objects/:id/history | Історія подій |
| GET /v1/notifications?after=:iso&afterId=:uuid | Нові повідомлення у доступних об'єктах; курсор за часом і UUID |

Запити працюють по HTTPS. API задуманий насамперед для **нативного C# HttpClient**, а не для пересилання токенів у вбудований WebView. За замовчуванням браузерні запити з Origin відхиляються.

## Що ще потрібно до повної синхронізації

1. Локальна черга змін із повторною доставкою після офлайну, автоматичний перехід до синхронізації та зняття локальних копій об’єктів після відкликання доступу.
2. Ручне публікування вже використовує стабільні UUID на основі походження запису. Потрібна повна двостороння синхронізація локальних архівів, приміток і файлів.
3. R2 для фото; маршрути, контури й сектори — окремий синхронізований шар.
4. Розширення наявної панелі: пошук, фільтри та черга призначень, системні сповіщення Windows; Telegram — тільки за окремою згодою.
5. Інтеграційні тести в Cloudflare D1, пробна інсталяція на **двох різних комп'ютерах**, перевірка роботи офлайн і конфліктів.

**Правило безпеки:** коли менеджер втрачає призначення, його серверні запити негайно блокуються. Локальні копії на офлайн-комп'ютері можуть існувати до наступного підключення; це треба відобразити в політиці зберігання даних.

## Перевірки

Виконати у корені репозиторію:

- node --check cloudflare/src/worker.mjs
- node --test cloudflare/tests/worker.test.mjs
- python3 -c "import sqlite3; sqlite3.connect(':memory:').executescript(open('cloudflare/schema.sql', encoding='utf-8').read())"

Ці перевірки запускаються GitHub Actions для PR. Вони **не замінюють** живих тестів із Cloudflare D1, R2 та Windows-клієнтом.
